## 0. 结论摘要

1. **一切 RSI 产出都只在本机、只为这个用户**:规则、踩坑、工作方法 / 技能、子代理、可执行物、能力缺口记录,全部进本机无远端的私有 git 仓库(`~/.local/share/agent-kit/personal/`),经本机灰度与机器闸自动生效、自动回滚。公开仓库只收「框架改进投稿」,由用户用自己的账号提交、维护者人工合并(§6)。
2. **人工采纳由五样东西替代**:确定性机器闸(零 LLM)、声明式固定测试(Medium 档,kit 固定解释器判定,不执行生成的 shell)、**按会话随机分组的灰度**(对照组不加载新改动)、拆分的回滚与独立撤销路径、熔断。任一不可用或超时,候选停住或到期,循环退回「只提示」,不会降档放行。
3. **没有真值,所以判定不对称**:判「变好」要目标问题显著下降 + 每项保护指标**非劣效**(置信上界低于预设界限,不是「没检出变差」)+ 事件数与精度门槛;判「变差」门槛低。证据不足默认不生效(M9)。低频问题多半拿不到统计生效,只作按需加载的技能。门槛先用本机历史数据做功效模拟(V1.5)再定。
4. **静态渲染是新阶段**(M12 B):灰度证据只对「按会话注入」成立;转静态后一次只转一个、单独监视、限定影响面,任一保护指标越过控制界即经撤销路径回滚。
5. **任意脚本 E1 可以自动启用,但有硬前置**(M5):只有本机存在**通过隔离验证探针 I1–I8**的容器运行时(无网络含宿主回环、只读挂载、挂载落点正确、资源上限、超时可杀、无特权、无凭据变量)、且用户看过探针报告后打开总开关,单个 E1 候选才自动启用;每次执行前还复核运行时指纹。探测不到或不通过就不启用并给归因;按评审判断,macOS 上很可能多数运行时不通过。用户决定 E1 试用通过后**在宿主上运行**(P2):启用后即用户完整权限,容器试用不能证明宿主上无害,所以另加执行前哈希复核、执行器强制层(写明哪些强制不了)、事后检测、每次审计,首次宿主运行与内容变化后的首次运行需用户确认一次。E1 排在最后一期;**macOS 上 E1 大概率不会启用**(P3)。
6. **第三方扩展**(M15 C):自动识别缺口、清点本地能力、搜索候选、非执行式检查;**首次执行第三方代码之前**请用户授权;离线安装已审阅的制品闭包;停用与尽力恢复。
7. **框架改进投稿**(§6,P1 已定):判据是「改进对象是 kit 自己的东西」(方法技能、闸规则、常量、kit 代码缺陷),由 kit 按目标路径机械判定,拿不准一律归个人层。投稿内容只含抽象描述与补丁,不含摘录与任何个人 / 项目特征;过泄漏闸;kit 不持有、不新建凭据;用户每次确认后,kit 调用用户自己的 `gh`,以固定命令形状从用户 fork 创建**草稿** PR,不做其他任何操作;任何失败静默降级为只导出草稿。
8. **预置技能保留**(M14):它们是框架内容,RSI 不改写它们;在灰度里两组都加载,是常量背景,不进对照、不被评估;与候选近重复时候选被拒。
9. **分期**:V0 契约 → V1 个人层「规则 / 踩坑」最小闭环(单候选、只经会话注入、判定默认关)→ V1.5 只记录 + 功效模拟 → V2 本机静态生效通道 → V3 流程 / 工作方法 / 技能 → V4 框架改进投稿 → V5 能力缺口与第三方扩展 → V6a 可执行物 E1 本体 → V6b 隔离探针与真机验证。粗估 49–65 人日,另含 7 项需用户当场同意的真实环境动作(§10.3)。

M14 保持现状,对灰度的影响:

- **预置技能不进对照范围**:两组会话都加载它们,是常量背景。灰度比较的是「加不加载候选」,预置技能对两组的影响相同,不引入偏差。它们自身的效果**不被评估**,也不会被自动退役。
- **交互作用与功效损失**:候选与预置技能说的是同一件事时,G4 的近重复检测(比对集合含预置技能)直接拒;功能重叠但措辞不同、没达到近重复阈值时,候选的增量效果会被预置技能吃掉,统计上很难判出变好、多半 `expired`——这是功效损失,不是偏倚。这类候选在闸里记 `overlaps_preset`,V1.5 的功效模拟把它单列;codex 不参与灰度,但会加载预置技能,codex 的统计一律单独做(§5.4)。
- **背景变化**:用户卸载 / 更新预置技能,或 npm 更新改变了包 payload,都会改变两组共同的背景。判定挂在「本机 payload 哈希」上:分组账每行记 `background_fp`(当时本机 payload 的哈希),评估器按 `background_fp` 分段,跨段不合并;之前的段只作敏感性分析。同一机制用于 §5.4 的前后对比。
- **预置技能有问题怎么办**:只能走 §6 投稿;个人层可以产出一条「与之相关的补充规则」,但不能覆盖或禁用它(G4 已禁止 override 非 `auto_rsi` 原子)。

### 3.2 存放位置(M1 A,已定)

`~/.local/share/agent-kit/personal/`:独立 git 仓库,**无远端**;kit 每次操作前校验「无 remote、属主是当前用户、目录 0700、工作树干净、HEAD 等于 kit 记录的提交」,结构性问题(有 remote、属主或权限不对、不是 git 仓库)→ 熔断 B4。HEAD 与记录不符按三态处理(评审 H10,机械判定):①HEAD 是记录提交的后代、只增加了文件且未触碰自动产出 → 接受并更新记录;②HEAD 是祖先、在别的分支、有 stash 或改了自动产出 → `personal_repo_diverged`,暂停新增(不熔断),提示用户二选一(回到记录提交 / 让 kit 以当前 HEAD 为新基线);③其余 → B4。kit 用分离 HEAD 之外的固定分支 `rsi`,用户切到别的分支即属情形②。它在 `HOME_WRITE_TABLE` 的 kit 条目之内,但写入经新增的「私有仓库提交」原语(§12)。「无远端」防的是误推,不防本机读取、备份与同 UID 泄露;`rsi purge` 对私有仓库额外做历史改写(§5.6)。

### 3.4 可执行物 E1:任意脚本,以隔离验证为前置(M5,已定)

用户决定:沙箱验证后自动启用任意脚本。本稿照此设计,并把评审与事实写成**前置条件**,而不是降低承诺:

**事实**(写清,不弱化):macOS 上没有经过验证的强隔离环境可以直接用;`sandbox-exec` 已弃用;`node --permission` 只约束 Node 进程;「命令白名单」不是安全边界(shell 的替换、重定向、展开让静态扫描守不住);一旦脚本由宿主上的钩子或 agent 直接调用,它就以用户全权限运行,试跑时的沙箱不随行。

**前置条件:隔离执行环境 + 隔离验证探针**

- 环境:本机存在容器运行时(Docker、colima、podman 等;P3 已定:任何通过探针的运行时都接受)。kit 不安装它,只探测。
- 探针 `agent-kit rsi isolation probe`(前台;worker 每 7 天与运行时版本变化时复跑)在一个固定的最小镜像里跑一组**正向对照 + 逃逸尝试**,全部满足才判 `verified`:

| 项  | 判据                                                                                                                                                                                                                                                            | 对照                                                                                                                                               |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| I1  | 无网络:分开记录三件事——①配置断言(运行时报告该容器的网络模式为「无」);②实际连通性:DNS 解析,以及对三种宿主回环入口(运行时提供的宿主别名、默认网桥网关、`host-gateway`)上 kit 临时起的监听服务的 TCP 连接;③覆盖限制(只测了这些路径与 TCP,不代表任意协议与目的地)   | **每条连通性路径各有正向对照**:用同一镜像、同一探测代码、只解除网络隔离再跑一次,该路径必须连通;正向对照不通的路径记 `unknown`,不能当作「隔离成立」 |
| I2  | 只读挂载:对挂载进来的输入目录写入失败                                                                                                                                                                                                                           | 对容器内临时目录写入成功                                                                                                                           |
| I3  | 挂载落点正确(拆为两项):I3a 未挂载路径不可见(只作对照,不断言,本身是恒真式);I3b 唯一可写挂载的宿主落点必须是 kit 新建的空临时目录,容器写入的文件在该目录出现,且宿主上同一父目录下的一个哨兵兄弟目录树哈希不变                                                     | 故意把可写挂载指到哨兵兄弟目录,判据必须报出(能抓「挂载参数指错到 HOME」)                                                                           |
| I4  | 资源上限:内存超限被杀;进程数上限生效;输出字节上限生效;CPU 用墙钟超时(不依赖 CPU 配额,因为 VM 下语义不一致)                                                                                                                                                      | 不设上限时同一负载能跑完                                                                                                                           |
| I5  | 超时可杀:超时后用运行时自己的列举命令(含已停止容器)查不到该容器 id,宿主进程表里没有该次调用派生的进程                                                                                                                                                           | 不设超时时同一负载会超过时限                                                                                                                       |
| I6  | 无特权:非 root 用户、丢弃全部 capability、禁止提权;容器内对运行时 socket 的常见路径(`/var/run/` 与 `/run/` 下的 `*.sock`)不可见,运行时客户端命令不可用                                                                                                          | 挂入 socket 时判据必须报出                                                                                                                         |
| I7  | 环境变量:宿主侧注入一组哨兵变量(覆盖 `KIT_*`、常见凭据变量名),容器内 `env` 一个都看不到;只传契约里写死的白名单                                                                                                                                                  | 宿主侧 `env` 确实含哨兵(两侧各断言一次)                                                                                                            |
| I8  | 平台能力:逐项记录「无网络、**只读根文件系统**(容器内对 `/` 写入失败,正向对照为可写根时成功)、内存上限、进程数上限、丢弃 capability、禁止提权」是否实际生效;另检查运行时只连本机实例——拒绝远端 context、远端守护进程与非本地 socket / 端点(否则输入会被送出本机) | 每项同样有解除该约束后的正向对照                                                                                                                   |

每项结果取 `pass / fail / unknown / error` 四态;**只有全部必需项为 `pass` 才判 `verified`**(必需项 = I1–I7 全部 + I8 中的无网络、只读根、丢弃 capability、禁止提权、本机实例);`unknown`(正向对照不成立)与 `error`(权限不足、命令缺失、超时、探针自身异常)都 fail-closed。归因分三类:「平台不支持」「配置不安全」「探针错误」。后台定时探针、前台 `rsi isolation probe` 与每次 E1 调用前的复核共用同一份验证策略。

- 探针结果记 `isolation.json`:`host_os`、`runtime_kind`(`native` / `vm`)、运行时名称与版本、运行时配置指纹(VM 参数与守护进程配置文件的内容哈希)、镜像摘要、探针版本、每项 `{ok, observed, expected, reason_code}`、时间;任一项失败 → `unverified`,E1 不启用。`rsi isolation probe --explain` 给可读归因(例如「这个运行时在 macOS 上做不到只读挂载」),让用户能区分 kit 的缺陷与环境不支持。
- **镜像固定**:探针与 E1 只用一个固定最小镜像,摘要写成契约常量 `ISOLATION_IMAGE_DIGEST`,每次使用前核对;镜像由用户在 §10.3 动作中同意拉取。
- **每次执行前复核**:每次 `exec-run` 先读运行时版本与配置指纹(轻量命令,毫秒级 [假设]),与 `isolation.json` 不一致 → 标 `unverified`、不执行、熔断 B11(对应评审的 B12 建议,合并进 B11);另外每 7 天复跑一次完整探针。残余窗口从「7 天」缩小到「一次调用之内」,但仍不为零。
- **探针通过不等于自动打开**:`[rsi.auto] exec = "host_after_trial"` 由用户看过探针报告后手动打开;打开之后,单个 E1 候选的启用才是自动的(M5 的「自动启用」指这一层)。
- 探针自身的验收(V6b):①**合成对照组**(CI 中用可控的假运行时):8 个变异——开网络、去只读、挂入运行时 socket、去掉丢弃 capability、去掉进程数上限、去掉内存上限、传入完整宿主环境、把可写挂载指到哨兵兄弟目录——每个变异预先登记三组项——必须失败的核心项、允许联动失败的项(例如挂入运行时 socket 同时影响 I6 与 I8)、不得失败的无关项——测试断言核心项失败、无关项不变、最终结果为 `unverified`(不要求「恰好一项」,以免诱导实现弱化检查);假运行时测试只验证探针逻辑,不证明真实运行时的隔离能力;另有「探针在全部项通过时才判 `verified`」的反向变异(把任一项的失败改成跳过,必须红)。②**真机对照组**:至少一台 Linux 宿主与一台 macOS 宿主各跑一次并记录;macOS 上允许 `unverified`,但必须是有归因码的已知原因,不能是探针崩溃。

**E1 的生命周期**

1. 会话 agent 交 `ExecManifest`:用途、触发方式(哪个工具调用或命令前后)、输入(只读挂载哪些路径,只许当前项目目录的子集)、输出(只允许 stdout 文本 ≤ 64KiB,或在容器内临时目录产出的补丁文件)、资源上限、超时、声明式断言(期望输出)。
2. 闸:G0–G7 + 脚本静态检查(结果只作线索);manifest 不得请求网络、不得挂 HOME、不得挂 kit 状态目录与私有仓库。
3. **隔离试跑**:在已验证的隔离环境里,用合成输入跑 manifest 声明的用例,按声明式断言判定;同时检查资源与超时没越限。
4. 灰度(评审 M8):容器试跑只是进入灰度前的门槛,**不作为宿主阶段的证据**。灰度本身就是宿主运行:按会话随机启用,被分到「启用」组的会话里由宿主执行器运行;**第一次宿主运行(即第一次 canary 运行)之前**必须完成第 6 条的人工确认,worker 不得因候选进入 canary 或 adopted 而直接启动未确认的宿主脚本。观察失败、超时、资源越限、事后检测结论与目标问题复发。
5. 生效(`adopted`):在 `exec-enabled.json` 登记;受总开关 `[rsi.auto] exec` 与首次运行确认约束(见下)。
6. **输入与输出的约束**(评审补的 TOCTOU 与回传):kit 在容器启动前对 manifest 声明的输入算内容哈希,容器内由 kit 注入的前置步骤先校验输入哈希,不一致即不运行脚本;脚本若产出补丁,补丁在交给 agent 之前必须过 G1、G2 与补丁安全检查(与 §18 C9 同口径),不过即丢弃;`exec-run` 全局并发 1(独立的 `exec/lock`,不用 `rsi/lock`),占用时返回 `exec_busy`,不让脚本排队超时以免污染失败归因。

**运行时在哪执行(P2,用户已定:宿主上运行)**

用户决定:E1 脚本通过隔离试用后**在宿主上运行**。这一条的真实含义写在最前面:**启用后脚本以用户完整权限在宿主上运行;容器试用通过不能证明它在宿主上无害**(试用环境没有网络、没有用户文件、没有凭据,脚本在宿主上看到的是另一个世界)。下表并列本稿原推荐与用户决定:

| 方案                                  | 含义                                              | 风险与代价                                                                                                           |
| ------------------------------------- | ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| A(原推荐,未采纳)运行时也在容器里      | 每次在已验证隔离环境里跑,效果只能是输出文本或补丁 | 容器启动开销;做不了需要宿主写或网络的事;macOS 上多半因探针不过而不可用                                               |
| **B(用户决定)试用通过后在宿主上运行** | 每次由 kit 的宿主执行器在宿主上跑,能做宿主上的事  | 用户完整权限;试用隔离不随行;观察期只能发现「坏了」,发现不了「做了不该做的事」;下面的硬约束只能缩小、不能消除这一风险 |

**宿主运行的硬约束(契约级前置,任一不满足即不执行)**

1. **授权身份与单次输入分开**(评审 M7):授权身份 = 脚本内容哈希 + manifest 哈希 + **执行闭包**哈希(manifest 声明的解释器路径与其二进制哈希、脚本引用的本地辅助文件)+ 策略版本;它必须与用户确认时一致,否则拒绝运行并回到 `shadow`。单次调用的实际输入每次做快照并记哈希(写审计),不要求等于试用时的合成输入。动态加载的系统库与解释器自身的依赖不被这些哈希覆盖,所以「哈希一致」不等于「执行内容完全一致」。
2. **执行器强制层**:逐项写明能不能强制:

| 约束           | 宿主上怎么做                                                                                                           | 是否强制                                                                                                                                                                                                                                                                          |
| -------------- | ---------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 超时终止       | 新进程组启动,超时后对整个进程组发 SIGTERM,宽限后 SIGKILL;结束后检查进程组为空                                          | **部分强制**:能终止仍留在受管进程组内的进程;**不保证**终止脚本自己新建会话 / 进程组的脱离进程,或交给其他宿主服务(定时任务、启动项、守护进程)的工作。超时或无法确认清理结果 → 停用候选、进 `manual_recovery_required`。Linux 上若改用经验证的 cgroup 可单列更强保证,不外推到 macOS |
| 环境变量白名单 | spawn 时显式给出环境(只含 manifest 声明且在契约白名单内的键,`HOME` 指向执行器建的临时目录),不继承父进程环境            | **强制**(脚本自己去读配置文件取凭据则不受此限)                                                                                                                                                                                                                                    |
| 资源上限       | 固定外壳先设 `ulimit`(CPU 时间、单文件大小、进程数、打开文件数)再 `exec` 脚本;外壳字符串由 kit 写死,不拼接任何外部文本 | **部分强制**(macOS 对进程数等上限的支持与 Linux 不同,逐项在 `isolation.json` 的平台能力里登记)                                                                                                                                                                                    |
| 输入只读       | 把声明的输入复制到执行器临时目录,只把副本路径交给脚本;原件不出现在参数与环境里                                         | **不强制**:脚本知道或猜到原路径就能读写原件。只能靠事后检测(第 3 条)                                                                                                                                                                                                              |
| 输出限定目录   | 工作目录设为执行器新建的输出目录,声明的输出只从这里取                                                                  | **不强制**:脚本可以写任意可写路径。只能靠事后检测                                                                                                                                                                                                                                 |
| 无网络工具     | `PATH` 只含一个由 kit 维护的精简目录(不含 curl、wget、ssh、nc 等)                                                      | **不强制**:脚本可用绝对路径或解释器自带的网络库。仅靠试用观察(试用环境无网络,但这只说明「没网时没出错」)                                                                                                                                                                          |
| 额外沙箱       | 若 `sandbox-exec` 可用,套一层禁网、限写的配置                                                                          | **不计入保证**:已弃用、行为随系统版本变化;只作尽力加固                                                                                                                                                                                                                            |

3. **事后检测**(评审 M6,保证收窄):运行前后对「项目目录(有大小上限)、HOME 下的受管路径」做树哈希(含文件类型、模式、符号链接目标;超出上限的目录记「未检」而不是「通过」;kit 自己的审计与 journal 写入不计入),出现声明之外的改动 → 停用该候选、记 `undeclared_write`、进 `manual_recovery_required`。它只能检测**受检范围内、结束时仍存在**的改动;读取、外发、写后复原、范围外写入、后台活动都不在覆盖内;检测本身失败按「未通过」处理。
4. **审计**:每次宿主运行写一行:候选 id、三个哈希、开始与结束时间、退出码、耗时、资源用量、事后检测结论;不写参数与输出内容。
5. **总开关**:`[rsi.auto] exec = "off" | "host_after_trial"`,缺省 `off`,只能由用户在看过隔离探针报告后手动打开(kit 只读配置)。
6. **E1 的人工确认特例**:**首次宿主运行**(即第一次 canary 运行),以及授权身份(脚本、manifest、执行闭包、策略版本)任一变化后的首次宿主运行,都要用户在 TTY 里确认一次:展示脚本全文、manifest、执行闭包清单、强制层表中「部分强制」「不强制」的各项与「遗留后台执行」风险。确认绑定授权身份哈希;确认后 kit 把已验证的脚本与辅助文件复制到执行器专用目录(0700),之后每次都执行这份固定副本、不再按原路径读取(消除确认与执行之间的替换窗口)。这不属于「去人」范围,是 E1 的明确特例;确认之后同一哈希的后续运行才是自动的。TTY 确认只是尽力区分人与脚本(R20-3.6.4)。
7. **交付顺序**:E1 在最后一期(V6a / V6b)交付,首个版本不含 E1。

**macOS 上的预期(P3,用户已定:接受任何通过探针的运行时)**:按第三轮评审判断,macOS 上的容器运行时都跑在虚拟机里,挂载、资源与网络语义与 Linux 不同,**预期多数运行时至少一项探针不通过,所以 macOS 上 E1 大概率不会自动启用**。`rsi status` 与 `rsi isolation probe --explain` 会如实说明原因。可替代路径(本稿不实现,只说明):①在 Linux 宿主上使用 agent 与 kit,探针更可能通过;②在隔离的 CI 环境里做试用——但这会把脚本内容送出本机,且 CI 环境与用户的 macOS 宿主差异更大,试用结论对宿主运行的代表性更弱,需要另行设计与授权。

**停用路径**(评审 H4 的语义):`disable_requested → disabled → cleanup_pending → uninstalled | manual_recovery_required`。`disabled` = 从 `exec-enabled.json` 删除(kit 自己的状态文件,立即生效,不依赖 agent);宿主运行过的脚本可能已经改过宿主文件,只能按事后检测记录尽力恢复可归属的改动,其余进 `manual_recovery_required`。总开关关闭等于停用全部 E1。

**残余风险**(照写):宿主运行时的用户完整权限,强制层表中「不强制」的四项完全依赖试用观察与事后检测;容器试用与宿主环境差异(网络、文件、凭据都不同),试用通过对宿主行为几乎没有约束力;容器逃逸(试用阶段);探针只证明调用前那一刻;镜像供应链;macOS 上 E1 基本不可用;TTY 确认可被有伪终端的 agent 冒充;事后检测有大小上限,范围之外的改动发现不了。

### 3.5 预算口径

- 自动产出占单独配额:每个渲染目标预算的 25%(claude 200 行中 50 行;其他 16384 字节中 4096 字节);代码常量,配置只能调严。配额内:规则 50%、踩坑 30%、技能触发描述 20%。
- 新增使配额占用 ≥ 80% 时,必须同时退役一条;做不到不生效。
- 灰度注入不占静态预算,但计入 M11 的注入上限(≤ 1.5KiB / 会话)。
- 预置技能(M14)不计入自动配额。
- 规则 50% / 踩坑 30% 是逻辑分类,渲染后共用 `rules` 文件的同一份预算。

### 3.6 能力缺口 → 自己找扩展补上(M15 C,已定)

用户举的例子:被要求做可点选的选择框,agent 回「没有原生选择框,我给你做个网页问卷」;用户追问「那 pi 有插件可以做到吗」。期望:以后遇到这类缺口,agent 自己去找合适的扩展来解决,并把「这类缺口怎么补」记下来。本节只设计机制,不调研具体插件。

**三个 artifact**:

| artifact             | 内容                                                                                                                                                                                    | 存放                                                    |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| `CapabilityGap`      | `agent`、`capability`(固定枚举 + `other`,如 `ui_choice`、`browser`、`image_read`、`pdf`、`db_query`、`notify`)、首次 / 最近出现、次数、识别来源、状态                                   | 私有仓库 `capabilities/<agent>/<capability>.md`         |
| `ExtensionCandidate` | `ecosystem`(`pi_package`、`claude_plugin`、`mcp_server` 等)、包标识、精确版本、完整制品清单哈希、来源仓库、发布者、`declared_permissions`、`observed_behaviors`、`enforced_permissions` | `.state/rsi/capability/candidates/`                     |
| `ExtensionAdoption`  | 采用了哪个候选(或「无可用候选,改用某替代做法」)、授权记录、安装时间、配置基线哈希、观察结果、状态                                                                                       | `.local/state/agent-kit/rsi/extensions.json` + 记录正文 |

记录正文是一条踩坑 / 工作方法,分三种状态写:「本机已安装且验证」「仅推荐候选」「未安装时的替代做法」。它走普通的灰度与生效流程,与扩展是否安装相互独立;负面结果(「没有合格的扩展」)同样记录,防止反复搜索。**记录正文不能充当安装授权**:agent 读到「用扩展 X」时只能发起授权请求。

**识别信号**(只触发调查,不推导安装必要性;「询问插件不等于同意安装」):

| 信号                      | 判据                                                                                  | 可靠性                                                          |
| ------------------------- | ------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| `agent_self_incapable`    | agent 回复里「没有原生 / 无法直接 / 不支持」等句式且给出替代做法;只记 capability 标签 | 中;需 reader 对助手消息做句式匹配(新增读取面,不入库原文 [假设]) |
| `user_asks_for_extension` | 紧接其后用户问「有没有插件 / 扩展 / MCP」                                             | 高,稀疏                                                         |
| `tool_missing`            | 工具结果为「工具 / 命令 / MCP 服务器不存在」(`tool_error_class=not_found` 子类)       | 中;也可能是拼错                                                 |

门槛:同一 `(agent, capability)` ≥ 2 个会话,或一次 `user_asks_for_extension`。`capability=other` 只记录,不进入搜索。

**授权边界 = 首次执行第三方代码之前**(第二轮评审 H1)。流程:

| 段       | 步骤                                                                                                                                      | 执行第三方代码 | 谁做                      |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------- | -------------- | ------------------------- |
| 自动段   | ①识别 → ②**本地能力清点**(已装扩展清单、原生工具枚举、配置诊断;去重只看这些可验证信息)→ ③搜索候选 → ④获取制品 → ⑤安全解包 → ⑥非执行式检查 | 否             | 会话 agent(①③④)、kit(②⑤⑥) |
| 授权     | 展示来源、版本、完整闭包、实际权限(无强制隔离时按「宿主完整权限」展示)、检查结论,请求用户授权                                             | —              | 会话 agent 发起,用户确认  |
| 授权后段 | ⑦离线安装已审阅的制品 → ⑧观察 → ⑨记录                                                                                                     | 是             | 会话 agent 执行,kit 核对  |

不做执行式试用(没有已验证隔离执行器之前;将来若用 §3.4 的隔离环境做试用,试用本身也算一次需授权的代码执行)。

**非执行式检查**(kit,确定性):

| 闸   | 判据                                                                                                                                                   |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| E-G0 | 安全解包:隔离目录的制品是不可信输入;拒绝绝对路径、`..`、链接、设备文件;限文件数与展开字节;文件类型白名单;产出完整制品清单哈希                          |
| E-G1 | 来源:发布者是否在用户的 `[rsi.capability] allow_publishers` 里(只影响展示,M15 C 下不影响是否需要授权)                                                  |
| E-G2 | 闭包固定:入口包与全部传递依赖、可选依赖、平台相关包、原生二进制都有精确版本与内容哈希;记录安装器及版本;拿不到完整闭包的生态标为「不支持」,只能人工处理 |
| E-G3 | 权限三栏:声明 / 静态发现 / 实际强制(多数宿主内扩展为「无」);声明超出 capability 模板即拒;通过不代表扩展只拥有模板权限                                  |
| E-G4 | 静态检查:安装脚本、子进程、动态求值、网络请求、运行时下载、对 HOME 敏感路径读写、混淆比例;命中在展示中标红。只是线索,不是安全边界                      |
| E-G6 | 去重与膨胀:同一 `(agent, capability)` 只允许一个 `trial` / `adopted`;每个 agent 经 kit 采用的扩展 ≤ 5;`adopted` 后 60 天无目标能力调用 → 停用候选      |
| E-G7 | 冷却:被拒或被停用的候选按「包标识 + 版本 + 闭包哈希」拉黑;同一缺口 30 天内不重复搜索(用户再次追问除外)                                                 |

哈希的信任薄弱点:制品与哈希都由会话 agent 从注册表取,agent 或注册表被攻破时可以一起被替换;E-G2 防「审阅与安装不一致」,防不了「来源本身恶意」。

**谁联网、谁执行**:搜索与获取由会话 agent 联网;解包与检查由 kit 离线;安装由会话 agent 离线执行(会执行第三方代码);运行由宿主 agent 每次会话执行。kit 进程自身零联网不变,但端到端流程新增了联网与第三方代码执行能力,需要独立授权契约(§12 第 30 条)。

**安装票**:绑定目标 agent、作用域(只做用户级)、制品清单哈希、预期配置差异、授权记录、策略版本;单次使用;出票时记配置基线哈希(不长时间持锁:安装是 agent 的外部行为,时长不可控;安装前后各算一次基线,与预期差异不一致即进 `manual_recovery_required`);安装前重新校验清单;安装器禁止重新解析或下载;安装脚本默认禁用,确需执行的在授权时单列。kit 不写 agent 配置(F8),只读来做基线与核对;配置备份 0700 / 0600,`restored` 后 30 天删除。

**停用与尽力恢复**:`disable_requested → disabled → cleanup_pending → uninstalled | manual_recovery_required`(`uninstalled` 只表示配置已恢复;`rsi status` 对每个 `uninstalled` 常驻一句「部署恢复不等于安全事件恢复」)。停用由会话 agent 用「不加载、不执行其卸载脚本」的方式移除,kit 核对;agent 起不来或停用失败时状态停在 `disable_requested`,下一次任何 kit 命令提示用户手动处理并给出要删的条目;只撤销可归属的配置差异,遇到无关改动即停。**部署恢复不等于安全事件恢复**:扩展对其他文件的改动、后台进程、外发数据撤不回,观察到可疑行为时提示用户按安全事件处理。

**观察**:`adopted` = 「运行兼容性观察通过」(20 个有观测会话无硬失败,且目标能力被调用 ≥ 3 次),不是安全证明。

**未授权时的记录**(评审 M8):用户不授权或 14 天无回应时,不产生灰度候选,而是在 `capabilities/<agent>/<capability>.md` 写一条负面记忆(只含 capability、日期、「未安装,替代做法:…」),不含摘录与项目特征,每个 agent 至多 50 条;同一缺口第三次出现时 hint 提示一次。它不经过 G0–G9,但有 schema 与上限。

## 5. D. 观察期与回滚

### 5.1 状态机(两个正交维度)

**候选生命周期**(私有仓库 + `.state/rsi/candidates/`):

| 状态           | 进入                                               | 退出                                                                                      |
| -------------- | -------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `proposed`     | ingest 成功                                        | G0–G7 全过 → `shadow`;任一红 → `rejected`                                                 |
| `shadow`       | 不渲染不注入,只统计「若存在会命中」                | 满 20 个会话且命中 ≥ 2 → `canary`;满 20 会话命中 < 2 → `expired`                          |
| `canary`       | 按会话随机注入 50%                                 | 判生效 → `adopted`;判变差 → `rolling_back`;到上限证据不足 → `expired`;G8 超时 → `blocked` |
| `blocked`      | 等待必需证据                                       | 证据到齐 → 回原状态;14 天 → `expired`                                                     |
| `adopted`      | 80% 注入、20% 留出                                 | 留出组 ≥ 20 个有观测会话(总计约 100 个)且非劣效 → `stable`;变差 → `rolling_back`          |
| `stable`       | 转静态渲染(新部署阶段,§5.4)                        | 控制界越限 → `rolling_back`;用户 `veto` → `rolling_back`;60 天无命中 → `retiring`         |
| `rolling_back` | 回滚请求                                           | 按 §5.5 四个子状态推进,完成 → `rolled_back`                                               |
| `retiring`     | 无命中退役                                         | 经撤销路径移除 → `retired`                                                                |
| 终态           | `rolled_back` / `retired` / `expired` / `rejected` | 进冷却(§5.6)                                                                              |

**本机部署**(每个候选):`none → injected → static_pending → static → removal_pending → none`。

「N 天」一律按「N 个有观测会话」计,用户不用 agent 时不前进;每个转移在实现里写成转移函数,带守卫、幂等键、时钟与恢复行为。

### 5.2 灰度怎么实现(M4 A、M13 A,已定)

- 会话开始钩子(claude `SessionStart`、pi `before_agent_start`)调用 `rsi hint`;hint 用注入随机源决定本会话是否附上 canary 文本,写一行分组账(会话开始时刻、agent、hint 生成的随机会话标记、候选 id、组别;无路径)。codex 会话不参与。
- 随机会话标记(固定前缀 + 16 位十六进制,字节计入 1.5KiB)写进注入文本,reader 采集时取回,用于关联 L0;取不回的会话计入 C6。标记能否进各家会话记录是 [假设],**V1 的准入条件**是在真实 claude 与 pi 会话里各验证一次「标记进了会话记录且能被 reader 取回」,不满足则该 agent 不开 canary。
- **注入文本不进评估指标**:注入文本带固定前缀与内容哈希,reader 识别后把它及其直接复述排除出显式教训、工具调用等计数(计入 C6 的完整率统计),并让 G1 / G2 对这段固定标记豁免——否则 canary 会污染自己的分母,下一轮还可能把注入文本当成注入模式。注入文本内固定写「自动产出、未经核验」。
- **适用资格在注入前确定**:资格 = 该项目在分组前 30 天出现过目标签名;不得用注入后的行为判断「本可命中」。主分析 ITT:所有被随机且资格成立的会话进分母,关联不上的按最坏情况做敏感性分析。
- M13 A:注入的只能是通过 G2 项目特征检测的通用规则,因此可跨项目注入;资格判定仍按项目。
- 每会话 canary 注入总量 ≤ 1.5KiB(M11)。

### 5.3 生效判据与样本量(数值待 V1.5 校准)

- **三重门槛**:每组 ≥ 20 个会话;对照组目标事件 ≥ 15 次;主判据率比双侧 90% 区间宽度 ≤ 0.6。
- **上限**:每组 120 个会话或 90 天,仍不满足 → `expired`(M9 A)。对照组发生率 0.1 次 / 会话时要约 150 个对照会话才凑够 15 次事件,超过上限——**低频问题拿不到统计生效是有意的结果**,它们改走按需技能。
- **检验**:不假设泊松独立,用按 agent × 项目分层的置换检验(2000 次);变好方向 α = 0.05 单侧、率比上界 ≤ 0.7;保护指标用 §4.4 的非劣效界限。
- **固定分析计划**:变差方向每 10 个新会话查看一次,O'Brien–Fleming 型 alpha spending,总 α = 0.10;变好方向只在门槛满足时与到上限时各看一次(各 α = 0.025)。错误率控制对象是每个候选;系统长期误生效率由 V1.5 的「无效果模拟」验收(注入无关文本,误生效率 ≤ 5%)。
- **长期累积口径**:每个候选的误生效率 ≤ 5% 不够——V1.5 的无效果模拟同时验收「每 100 个候选至多 5 个误生效,且误生效的候选在 stable 监视期内被回滚的比例 ≥ 50%」;长期按日历计至多每月 1 次误生效(超过即熔断 B1 同类处置)。
- **V1.5 功效模拟**:用本机真实历史信号的发生率与过度离散做重抽样,算出上限内可检出的最小效应量;若常见聚类都检不出 30% 的改善,统计生效通道在本机不可用,循环保持只提示,并如实告诉用户。

### 5.4 adopted 与 stable(M12 B,已定)

- **adopted**:80% 注入、20% 留出,留出组按 §5.3 的序贯边界监视;留出组 ≥ 20 个有观测会话且非劣效 → `stable`。
- **评估中的候选全局上限**:同一时间只允许**一个**候选处于 canary、adopted 或静态监视期中的任一状态(串行化),避免两个候选的监视期互相改变对照环境。
- **stable = 静态渲染,是新的部署阶段**:灰度证据**只适用于原注入模式**(加载位置、优先级、适用 agent 都变了),不得作为静态阶段的效果证据。静态阶段的规则:
  - **限制影响面**:先只对 claude 与 pi 渲染;codex 目标在 claude / pi 监视期结束、且 codex 自身已有 ≥ 20 个转前会话后才渲染,codex 再单独走一个监视期。
  - **监视方式**:按 agent 分别做转前 vs 转后的前后对比(按 `background_fp` 分段),承认其混杂,**只用于触发回滚、不用于证明效果**。
  - **三种结论**(评审 H6):①**检出伤害**:C1–C3 任一的转后 / 转前率比**下界** > 1;或 C6 采集完整率的「转前 − 转后」差值**下界** > 5 个百分点(差值判据,不用率比)——均按 §5.3 的序贯边界,单侧 α 总计 0.10 → 回滚;②**证实非劣效**:C1–C3 率比上界低于 §4.4 界限,且 C6 差值上界 < 5 个百分点 → 该 agent 的监视期通过;③**证据不足**:两者都不满足 → 继续观察。C4 越过绝对上限、用户 `veto`、熔断 B3 直接回滚。零事件用条件二项的精确区间,两组均为零事件算「证据不足」。**判定时点**:转后 ≥ 20 个会话起每 10 个会话查伤害;转后 ≥ 40 个会话起才允许判「通过」。
  - **分母定义**(评审 M9):会话数一律指「有完整观测、资格成立的会话」(C6 的分母例外,用全部被渲染的会话);另记事件数。转后 40 个会话起每 10 个会话判一次是否通过,未通过且未检出伤害则延长;转后 120 个会话仍未证实非劣效 → **撤回静态部署**:claude / pi 回到注入模式(80% / 20%);codex 不参与随机注入,其静态部署撤回后对 codex 保持关闭。codex 独立维护转前 / 转后数据、`background_fp` 分段与精度门槛。
  - 监视期结束后,长期按 agent 分别用控制图(C1–C3 的 28 会话滚动率越过监视期估计的 99% 上界 → 回滚);控制图常量是代码常量。

### 5.5 回滚:补偿流程

| 子状态                   | 动作                                                                                                                                                                                            | 完成判据                    |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------- |
| `rollback_requested`     | 写 journal                                                                                                                                                                                      | 落盘                        |
| `injection_disabled`     | 分组账标停止注入,下一次 hint 即不注入                                                                                                                                                           | 标记落盘(新会话不再受影响)  |
| `static_removal_pending` | 用候选集合 + 内容寻址快照重建私有仓库目标树并提交(不依赖 `git revert`);重渲染本机 payload(只对回滚目标做差量:以「上次已同步版本减去回滚目标」为目标,不顺带生效处于 `static_pending` 的其他候选) | HEAD 的树等于目标树         |
| `rollback_complete`      | 经**撤销路径**同步 HOME                                                                                                                                                                         | HOME 中该候选的托管块不存在 |

**撤销路径**:只允许删除自动产出的托管块 / 独占文件,不受 `auto_paused`、候选状态条件、操作数上限阻挡;仍遵守漂移规则(用户改过 → 不覆盖,停在 `static_removal_pending` 并提示)。自动产出一律写独立托管块或独占文件。崩溃后按 journal 续做,续做再崩溃同样可续。

审计 `.state/rsi/audit.jsonl`:无路径、无文本;保留 365 天、上限 20000 行,超出先按月汇总再删;分组账保留到候选终态后 90 天,之后只留聚合计数;只能称「kit 路径可追踪」。

### 5.6 防止重复提出

| 机制         | 内容                                                                     | 关系                                                                                                     |
| ------------ | ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| 聚类冷却     | 自动回滚 90 天、`expired` 30 天,期间不进 digest                          | 与 tainted 独立(冷却是质量处置)                                                                          |
| 文本指纹     | 规范化正文的 HMAC(本机密钥)与近似指纹,与冷却同期失效,只在本机            | —                                                                                                        |
| 用户否决     | `rsi veto` 的候选指纹永久黑名单;只能前台 `rsi veto --lift <id>` 解除     | 与自动回滚冷却分开                                                                                       |
| 墓碑         | 终态 id 进墓碑,C7 拒复用                                                 | 同现有机制                                                                                               |
| tainted      | 证据项目被排除 / purge:候选永不进灰度;已生效的进 `rollback_requested`    | N6 扩展。「立即生效」收窄为:下一次 hint 起不再注入、不再作新证据;静态撤销单独报告完成;已进上下文的收不回 |
| 私有仓库历史 | `rsi purge` 对私有仓库做历史改写并报告;备份与系统级快照不在 kit 管辖范围 | —                                                                                                        |

## 6. E. 框架改进投稿(取代原「团队层自动合并」)

### 6.1 判定:哪些改进属于框架层

框架层 = 改进对象是 **kit 自己的东西**;其余一律个人层。kit 按**目标**机械判定,agent 的自报只作提示:

| 框架层目标                            | 判据                                                                                                 |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 框架方法技能、预置技能的措辞          | 候选目标路径是 `agent-kit-rsi`、`agent-kit-capability` 或预置技能(G4 本来就拒绝自动改写它们)         |
| 闸规则缺口(词表漏报 / 误报、模板缺项) | 候选指向闸常量表的某一项,并附「被误拒 / 漏放的合成样例」                                             |
| 统计常量、隔离探针项                  | 指向契约常量                                                                                         |
| kit 代码缺陷                          | 证据来自 kit 自己的稳定码(`RSI_FAIL_CLOSED reason=internal`、`gate_internal`、reader 解析异常计数等) |

拿不准(目标既不是框架路径、证据也不是 kit 自己的稳定码)→ 个人层。

误判后果:

| 方向                             | 后果                                                                 | 缓解                                                                                                              |
| -------------------------------- | -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 个人 → 误判为框架                | 个人习惯被写进公开 PR 草稿,隐私风险;给维护者添噪音                   | 泄漏闸;用户逐次确认;草稿默认不出本机                                                                              |
| 框架 → 误判为个人                | 这个用户在本机绕过了问题(例如补一条个人规则),修复没有回到框架;影响小 | 个人层候选若被 G4 以「目标是框架路径」拒绝,只生成「抽象描述 + 合成样例」形态的草稿,不保留任何候选正文(防反向泄漏) |
| 用户 `veto` 过的问题被判为框架层 | 仍可能生成草稿                                                       | veto 指纹命中 → 该目标的草稿生成暂停 30 天;之后生成时标注「你否决过相关个人层候选」                               |

### 6.2 投稿内容的最小化与隐私

- 只允许三种内容:①抽象描述(问题是什么、为什么是框架问题,≤ 1KiB,固定模板);②对框架文件的补丁(方法技能文本、闸常量表、代码);③合成样例(由 agent 现写的、与会话无关的最小复现)。
- **不得包含**:会话摘录(哪怕已脱敏)、项目名与路径、用户名与主机名、精确计数与日期(只允许固定四档 `≥1 / ≥2 / ≥10 / ≥50` 个会话,由 L7 检查)、信号 id、私有仓库内容。
- 草稿落在 `.state/rsi/contrib/<id>/{patch, pr-body.md, check.json}`,0600;30 天未处理自动删除。`rsi contrib export <id> --out <目录>` 只接受用户显式给出、`realpath` 后仍在 HOME 内、链上无符号链接、目录尚不存在的路径(新增独立写原语,§12)。

### 6.3 泄漏闸(生成草稿时与提交前各跑一次)

| #   | 检查                                                                                                                                                                                                                                                                                                                                   |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| L1  | 脱敏器 pass2 全文扫描,命中即拒                                                                                                                                                                                                                                                                                                         |
| L2  | 项目特征:项目索引里的目录名、`exclude_names`、HOME 路径、当前用户名与主机名,出现即拒                                                                                                                                                                                                                                                   |
| L3  | 与信号库摘录的重合:**只豁免**令牌绑定的上游 `base` 提交中、补丁原位置上的未修改上下文行与删除行;所有新增行、移动到新位置的文字、PR 标题与正文、提交说明全量参与比对。剩余文本中任一连续 16 字(英文 8 词)与信号库任一 `excerpt_redacted` 重合即拒;「agent 名 + 工具名 + 失败类别」三者在同一段落同现即拒。L1、L2、L4 不因任何豁免而跳过 |
| L4  | 邮箱、IPv4、非白名单 URL 字面量、疑似凭据赋值(与仓库 A10 同一套规则)                                                                                                                                                                                                                                                                   |
| L5  | 路径:补丁触及的文件集合必须**完全等于** `check.json` 里登记的 `target_paths`;每个路径由 kit 按 §6.1 机械判定属于框架四类之一,不依赖 agent 判断「与描述一致」;契约文件(`docs/contracts.md`、`src/contracts/**`)允许,但只能是追加形状(不改既有行);不改 `.github/`、`package.json`、锁文件、`CODEOWNERS`                                  |
| L6  | 大小:补丁 ≤ 16KiB、描述 ≤ 1KiB                                                                                                                                                                                                                                                                                                         |
| L7  | 数值形态,按部位分别约束:PR 标题与正文、提交说明只允许版本号与四档分档门槛,不得有其他裸整数与日期;代码与常量表的补丁行不做裸整数限制(否则必然误拒合法代码),但新增行里出现日期字面量即拒;合成样例不限制                                                                                                                                  |

通过后在 TTY 里**完整展示**草稿全文,标「将公开」。L1–L7 是**启发式**泄漏检测:字面匹配识别不了编码、拆分、改写与组合泄漏;通过泄漏闸不等于可以安全公开,最终由用户在确认时判断。扫描对象是完整的公开制品(§6.4 第 3 步),不只是补丁。

### 6.4 提交方式(P1,用户已定:每次确认后由 kit 调用用户的 `gh` 开草稿 PR)

kit **不持有、不新建**任何凭据;它在用户每次确认后,以用户本机已有的 git 与 `gh` 登录状态执行。**自动路径永不推送、永不开 PR**(R20-1.8 对自动路径不变);只有前台命令 `agent-kit rsi contrib submit <id>` 能做这件事。

**先写清这不是什么**:固定命令形状**不是**对管理员身份的权限隔离。用户的 `gh` 登录很可能是 agent-kit 仓库管理员(admin 角色可绕过 v\* tag 保护,G3)。分两层看最坏情况:

| 层                     | 最坏情况                                                                                                                     |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 执行出口按契约工作     | 以用户账号公开一个分支和一个草稿 PR,触发通知与仓库对 PR 的自动化(工作流会以 PR 内容运行);内容只受泄漏闸约束,泄漏闸是启发式的 |
| 出口或其受信子进程失守 | 子进程手里就是用户的完整凭据,kit 没有能力把它限制为「只建草稿 PR」——包括合并、改规则集、读写 secret、发布                    |

所以下面的约束目标是:**kit 在正常执行时不意外继承、不意外扩大任何能力**;它不防同 UID 的主动篡改(R7)。

**模块边界**(评审 M11):草稿生成(`src/rsi/contrib/draft/**`,worker 可用,零子进程)、前台发布(`src/rsi/contrib/publish/**`,只由 `rsi contrib submit` 引用)两块分开;自动入口的 import 闭包不得含 `publish/**`。

**fork 身份**(评审 H2):`[rsi.contrib] fork_owner` 只接受 GitHub 用户名字符集(`[A-Za-z0-9-]`,1–39 字符,不以连字符开头或结尾);仓库名固定为 `agent-kit`;kit 由这两个组件构造唯一的规范地址(SSH 形式),不接受 URL、remote 名、端口、协议或路径。`fork_owner` 等于上游 owner(不区分大小写)即拒。kit **不验证**它确实是上游的 fork(那需要额外的只读查询能力);保证因此写作「推送到用户显式配置的、非上游的同名仓库」。

**封闭的 git 执行配置**(评审 H1):所有 git 子进程都在 `KIT_TMP` 下新建的临时仓库里运行,并且:

- 环境:`GIT_CONFIG_NOSYSTEM=1`、`GIT_CONFIG_GLOBAL` 指向 kit 生成的空文件、`GIT_TERMINAL_PROMPT=0`;清除继承的全部 `GIT_*` 与 `GIT_CONFIG_*` 变量后只设上述几个;`HOME` 保持用户 HOME(SSH 需要它)。
- 每条命令前置固定的 `-c` 参数:`core.hooksPath` 指向空目录、`init.templateDir` 置空、`protocol.allow=never` 且只放行 `protocol.ssh.allow=always`、`core.fsmonitor=false`、`transfer.fsckObjects=true`;不设置任何 `url.*.insteadOf` / `pushInsteadOf`(全局与系统配置已屏蔽,所以用户的重写规则不生效)。
- 作者身份:从用户全局配置**只读取** `user.name`、`user.email`、`user.signingkey`、`gpg.format` 四个值,校验字符集后以 `-c` 显式传入;其余全局配置一概不继承。
- **明确授权的间接执行能力**(列入契约,用户在 §10.3 第 8 条同意):①SSH 客户端(使用用户自己的 SSH 配置与 agent,用于推到 fork);②签名程序(`gpg.format=ssh` 时为 `ssh-keygen`,`openpgp` 时为 `gpg`,只接受这两种,路径在确认时解析并记录)。除此之外,git 不得调用任何外部程序:凭据助手、过滤器、远程传输助手一律不配置。

**发布对象先构建、再确认、确认什么就发布什么**(评审 H3):

1. 在临时仓库里 `git fetch` 上游 main(规范地址常量),记下 `base` 提交;建分支 `refs/heads/rsi-contrib/<id>`(`<id>` 只含 `[a-z0-9-]`,由 kit 生成);`git apply --check` 后应用补丁;以固定模板写提交说明(文件)并提交,得到 `head` 提交。
2. 校验完整的 `base..head`:恰好一个提交;改动文件集合等于 `check.json` 的 `target_paths`;只允许普通文本文件、模式 100644;拒绝符号链接、gitlink、二进制补丁、可执行位变化、重命名到 `target_paths` 之外。
3. **公开元数据全部枚举**:①提交的完整差异、②提交说明(固定模板)、③分支名、④PR 标题(固定模板)、⑤PR 正文的**固定副本**(写进临时目录、只读,`gh` 读的就是这份)——这五项全量跑泄漏闸 L1–L7;⑥作者与提交者身份:两者都设为第 2 节读出的同一组 `user.name` / `user.email`,**这一对精确值**是 L4(邮箱)与 L2(用户名)的唯一受限豁免,豁免值写进确认令牌,其余任何位置出现同样的值仍被拒;⑦作者与提交者时间:两者都固定为 `base` 提交的提交者时间(经 `GIT_AUTHOR_DATE` / `GIT_COMMITTER_DATE` 设置),不泄露本机时间与时区;⑧签名块(启用签名时):含用户的签名公钥身份,属于用户已在 GitHub 公开的身份信息,作为受限豁免并在确认时展示。⑥⑦⑧之外不存在其他公开元数据;若 git 版本产生了未列出的头部字段,校验 `base..head` 时即拒。
4. TTY 完整展示上述全部内容与将执行的三条命令;**确认令牌**绑定 `base` 提交、`head` 提交、正文副本哈希、上游仓库、fork、分支名;单次使用、10 分钟过期;执行前逐项复核。
5. 推送已确认的提交本身:`git push <fork 规范地址> <head 提交>:refs/heads/rsi-contrib/<id>`(不带 `--force`,不推其他引用)。
6. 开草稿 PR(见下)。

**`gh` 调用**(评审 M1):以确认时解析并记录的绝对路径、argv 数组、不经 shell 执行唯一形状 `pr create --repo <上游常量> --base main --head <fork_owner>:rsi-contrib/<id> --draft --title <固定模板> --body-file <正文副本路径>`。每个变量的类型与来源:`fork_owner` 来自校验后的配置;`<id>` 来自 kit 生成;正文副本路径来自 kit 新建的临时目录;标题模板只插入 `<id>`。环境只传 `PATH`(kit 的精简目录 + `gh` 所在目录)、`HOME`、`GH_PROMPT_DISABLED=1`、`GH_NO_UPDATE_NOTIFIER=1`、代理变量;清除继承的全部 `GH_*`、`GIT_*`。别名与扩展:`gh` 的内置子命令不能被别名或扩展覆盖 [假设,以所用 `gh` 版本实测为准,V4 验收项],kit 只以内置子命令名调用;二进制内容是否变化不核验(只核 `realpath`),同 UID 替换二进制属 R7 残余。超时 60 秒。

**结果四态**(评审 L2 与第五轮):

| 结果                        | 判定                                                                                            | 用户看到                                                                                                                               |
| --------------------------- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 无远端变化                  | 推送命令**未发出**之前任一步失败(`gh` / git 缺失、配置不合规、泄漏闸、确认令牌失效、fetch 失败) | 一行 `RSI_CONTRIB_DEGRADED reason=<码>`;草稿经 §6.2 的导出守卫写到 `[rsi.contrib] export_dir`(未配置则留在 `.state/rsi/contrib/<id>/`) |
| 推送结果未知,分支可能已公开 | 推送命令已发出,但失败、超时或连接中断(远端可能已接受提交)                                       | 稳定码 `RSI_CONTRIB_DEGRADED reason=push_unknown` + fork 上的分支名;提示用户去 fork 查看;草稿同样导出;不重试、不声称无副作用           |
| 已推送、PR 未确认           | 推送成功,`gh` 失败或超时(超时可能是远端已创建、本地没收到响应)                                  | 稳定码 + fork 上的分支名;提示用户去 fork 查看;kit 不重试、不清理远端分支                                                               |
| PR 创建成功                 | `gh` 退出 0 且 stdout 解析出 PR 编号                                                            | PR 编号;写审计                                                                                                                         |

频率:全局一周至多 1 次提交;同一框架目标累计至多 3 次。

**kit 不做**:合并、关闭、评审、编辑 PR;读写 secrets、规则集、发布、工作流;创建或删除仓库与 fork;删除远端分支;修改用户的 `gh` 或 git 配置。

### 6.5 与评审 H5 的关系

v3 评审 H5(个人层稳定证明可被同 UID 伪造,却被当作团队自动合并的依据)**部分消解**:个人层的证据只决定这个用户自己机器上的生效,不再外溢到他人;框架投稿不以个人层灰度报告为合并依据,由维护者人工判断。但「同 UID 可伪造分组账,让变差候选在本机被判为生效」这条路仍在,只是影响面限在本机,见 R7。投稿 PR 里可以附「本机观察到的分档计数」作为参考,但明确它不可验证。

## 7. F. 本机生效

### 7.1 与 §19.6 的衔接

本机生效 = 本机 payload 经 `safe` 条件写入 HOME。§19.6 原条件全部保留;改动与新增:

| 条件                                                         | 处理                                                                                                                     |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |

### 7.2 两种 payload 的隔离

- 登记表条目加 `source: package | local`;`check-publish` 断言包 payload 中不存在 `layer=personal` 或 `origin=auto_rsi` 条目;方法技能只从框架源码固定路径取,核对来源路径与文件集合(防同名替换)。
- `sync --rollback` 对两种来源一视同仁。

## 9. H. 度量与可见性

- `rsi status --json` 新增:`auto`(`{enabled, paused, pause_reasons, profile}`)、`pipeline`(各状态计数及 30 天的 rejected / rolled_back / expired / retired)、`budget`(自动配额占用)、`cost`(每会话注入字节、S2 次数)、`canary`(id 与两组会话数)、`static_watch`(当前监视期候选与剩余会话数)、`isolation`(探针状态与原因码)、`extensions`(trial / adopted / 待授权数)、`contrib`(待处理草稿数)、`last_rollback`。只含 id、枚举、计数。
- 周报:每周第一次会话的 hint 用周报行**替换**计数行(仍 ≤ 200 字节;「本周已报」用与 hint 去重同一机制的独占标记,§12):生效 a、回滚 r、灰度中 c、待授权扩展 x、投稿草稿 d、配额 q%。
- `rsi report [--week|--since <日期>]`、`rsi show <id>`(TTY、剥控制序列、标「自动产出」)。
- 一键操作:`rsi auto pause|resume`、`rsi veto <id>`、`rsi rollback --to <日期> [--write]`(按生效逆序逐个回滚,默认干跑)、`rsi auto clear [--write]`(撤掉全部自动产出,不删审计与黑名单)、`rsi stop`(连采集一起停);`[rsi.auto] exec = "off"` 停用全部 E1。
