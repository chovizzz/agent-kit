## 0. 结论摘要

1. **人工采纳由五样东西替代**:确定性机器闸(零 LLM,kit worker 跑)、声明式固定测试(可选档,由 kit 的固定解释器判定,不执行生成的 shell)、**按会话随机分组的灰度**(对照组不加载新改动)、自动回滚、全局熔断。任何一样不可用或超时,候选**停住或到期**(`blocked` / `expired`),循环退回「只提示」(v2 行为),不会降档放行。
2. **最大的结构性风险是「没有真值」**:我们没有基准测试集,所有闸都只能用代理指标判断「变好了」。本稿的应对是**不对称**:判「变差」的门槛低(一项保护指标显著变差即回滚),判「变好」的门槛高(目标聚类复发率显著下降 + 每项保护指标**非劣效**——置信区间上界低于预设退化界限,不是「没检出变差」+ 事件数足够);证据不足时默认**不生效**。评审指出且本稿接受:按每组 15–30 会话、低频事件的现实,**多数低频规则拿不到统计生效**,它们只能作为按需加载的技能存在;具体门槛必须先用本机历史数据做功效模拟(V1.5)再定。
3. **仓库是公开的**(实测 `visibility=public`)。所以「个人层全自动」**不能**合入公开仓库:个人层产出放在本机一个**无远端的私有 git 仓库**(推荐 `~/.local/share/agent-kit/personal/`),有提交历史、可 revert、可审计;团队层 PR 才进公开仓库,且**不带任何会话摘录**(证据只留随机 id 与计数)。
4. **可执行类改成「数据化」**:自动循环只产出「由 kit 自带的固定解释器执行的声明式数据」(如钩子拒绝规则表、命令别名表),解释器本身经人工发版、不在自动循环里改。任意脚本代码的自动启用列为备选,默认不做(§3.4、决定 M5)。原因:macOS 上没有能约束「已启用钩子在宿主 agent 里运行」的可靠沙箱,沙箱只能约束试跑,启用后就是用户全权限。
5. **自动合并不让本机持有能绕过保护的凭据,也不让投稿通道碰到合并凭据**:本机推候选到一个**独立的投稿仓库**(推荐,决定 M6),原仓库里从默认分支运行的工作流读取候选、开 PR、合并;合并用的 GitHub App 私钥只放在**部署分支限定为 `main` 的 environment** 里。原因(评审 H1):能向原仓库推任意分支,就能推一个带新工作流的分支并在 `push` 事件下执行任意代码,所以投稿凭据必须与原仓库隔离。发版(npm)**不纳入**自动循环。上述 GitHub 权限结论在 V4 用测试身份实测之前都是假设。
6. **团队 PR 不是即时合并**:**当前 head 提交**首次通过全部可信检查后,再保持 **72 小时否决窗口**,head 一变就重新计时;合并动作带预期 head 提交号。窗口、暂停开关、否决记录都由服务端维护,不信本机。这一条替代四眼:不要求人做动作,但保留人能拦的时间。**威胁模型照写**:团队层只防「kit 自己出错」,不防「本机 agent 被攻陷」——本机的灰度报告与稳定天数可被同 UID 伪造,服务端能验的只有内容范围与格式,所以团队自动合并实质上是一个**受限内容的无人审批投稿接口**;用户若要防本机被攻陷,团队层应停在「自动开 PR」(决定 M7 选项 B)。
7. **本机生效**新增一条「本机 payload」通道:kit 用本机私有仓库 + 已合并的团队层在本机渲染 payload,按 §19.6 的同一套条件(必须保留:非可执行、无 `must`、操作数 ≤ 20、重扫干净、无漂移、不扩 agent 集合、不首装)评估后写入;每次写入都是 sync 事务,`sync --rollback` 可回。需要修订契约 §19.1 ①「只从包内 payload 装」与 §4.2「personal 不渲染」。
8. **循环靠用户用 agent 推动**:生成提案与(可选)生成测试只能在用户会话里做(S2 续跑);闸、灰度分组、评估、回滚、本机写入、推分支全是 kit 后台 worker 的确定性步骤(零 LLM)。用户不用 agent 时循环停在当前阶段,灰度期计时暂停(按会话数而不是按天计),不会因为没人用而「到期自动生效」。
9. **分期**:V0 契约 → V1 个人层「规则 / 踩坑」最小闭环(单候选、只经会话注入、含自动回滚)→ **V1.5 只记录不判定 + 功效模拟,通过才开判定** → V2 本机生效通道 → V3 流程 / 工作方法 / 技能 → V4 团队层(先做权限实测,再做流水线)→ V5 数据化可执行物(先只 `warn`)。粗估 45–60 人日(评审 L3 后上调,其中 V4 权限实测与统计模拟不确定性最大),另含 8 项需要用户当场同意的真实环境动作(§10.3)。

### 2.2 替代保证的组成

| 保证     | 作用                                                          | 能挡住什么                         | 挡不住什么                                     |
| -------- | ------------------------------------------------------------- | ---------------------------------- | ---------------------------------------------- |
| 机器闸   | 结构、安全、预算、成本、重复、冲突的确定性检查                | 格式错误、注入话术、膨胀、越权路径 | 内容合乎格式但方向错误的改动                   |
| 随机灰度 | 一半会话加载改动、一半不加载,比较代理指标                     | 「看着合理但实际变差」的改动       | 代理指标看不到的退化;样本不足时什么也判断不了  |
| 自动回滚 | 指标变差、熔断触发、用户否决时撤回                            | 已生效改动的持续伤害               | 回滚前已发生的影响(已进模型上下文的内容收不回) |
| 熔断     | 系统级异常时整体退回「只提示」                                | 连环错误、自我强化                 | 熔断条件没覆盖到的异常                         |
| 审计日志 | 每次生效 / 回滚 / 拒绝留一行,带提交 id 与指标                 | 事后不可追溯                       | 不阻止任何事,只让事后能查                      |
| 否决窗口 | 团队 PR 当前 head 全绿后保持打开 72h,head 变化重计;服务端维护 | 用户看到后想拦的改动               | 用户没看到的改动(它不要求人看)                 |

### 2.3 熔断:自动退回「只提示」的条件 [推荐]

触发任一条即进入 `auto_paused`(循环的所有自动生效与合并步骤停止;采集、提示、提案、闸照常,结果只给用户看,即 v2 行为),原因码写进 `rsi status`:

| #   | 条件                                                               | 原因码                  | 解除                                 |
| --- | ------------------------------------------------------------------ | ----------------------- | ------------------------------------ |
| B1  | 30 天内自动回滚 ≥ 3 次                                             | `rollback_storm`        | 用户前台 `rsi auto resume`           |
| B2  | 任一闸的实现报内部错误(不是「判红」,是闸本身崩溃)                  | `gate_internal`         | 同上                                 |
| B3  | 本机 payload 渲染或 sync 事务失败、残留 txn                        | `apply_failed`          | `sync --resume/--rollback` 后 resume |
| B4  | 个人层私有仓库校验失败(有远端、工作树脏、HEAD 不是 kit 记录的提交) | `personal_repo_invalid` | 修好后 resume                        |
| B5  | 规则预算占用 ≥ 90%(`threshold_percent`)                            | `budget_high`           | 退役腾出空间后自动解除               |
| B6  | 7 天平均每会话注入字节(自动产出部分)比生效前基线上升 > 20%         | `cost_up`               | 自动解除(回落后)                     |
| B7  | 信号采集中断 ≥ 7 天(没有数据就无法观察)                            | `no_observation`        | 采集恢复后自动解除                   |
| B8  | 脱敏规则版本变化,或 `redaction.md` 的 `known_gap` 新增             | `redaction_changed`     | 用户 resume                          |
| B9  | 用户否决(关闭团队 PR、`rsi veto <id>`)7 天内 ≥ 2 次                | `user_vetoes`           | 用户 resume                          |
| B10 | kit 主版本变化                                                     | `kit_major_changed`     | 用户 resume                          |

`auto_paused` 不是安全阻断(契约 R20-6.5 的 `safety`)的替代:后者照旧停掉采集。

**本机暂停 ≠ 远端暂停**(评审 H4):`auto_paused` 只停本机的生效与推送;已在服务端排队的 PR 由服务端开关控制(仓库变量 `RSI_AUTOMERGE`,用户在 GitHub 界面改,见 §6.3)。`rsi status` 分别显示两者,本机不能确认远端已暂停时显示「远端仍可能合并」。

**回滚不受熔断阻挡**:`auto_paused` 下仍允许「只减少影响」的撤销路径(§5.5),不允许任何新增。

### 3.4 可执行类的分级

| 级别               | 内容                                                                                                               | 推荐                                                  |
| ------------------ | ------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------- |
| E0 数据化(推荐)    | kit 自带一个固定解释器(由用户一次性装好的钩子 / pi 扩展调用 `agent-kit rsi exec-check`),自动循环只改它读的数据文件 | 自动启用,总开关 `[rsi.auto] exec_data = false` 缺省关 |
| E1 受限脚本        | 自动生成的 shell 脚本,在沙箱里试跑                                                                                 | 不做(见下)                                            |
| E2 任意钩子 / 工具 | 自动生成程序并注册为钩子                                                                                           | 不做                                                  |

E0 解释器约束:只读当前工具调用的命令名与参数(钩子传入),只能返回 `allow | warn <固定文案 id> | deny <固定文案 id>`;文案只能从解释器内置的文案表选,数据里不能带自由文本(防止数据变成给 agent 的注入通道);匹配语法是「命令名精确 + 参数前缀 / 有限 glob」,无正则;数据 ≤ 50 条、每条 glob ≤ 3 个通配、单次匹配步数有上限。**首版只开 `warn`**,误报率经观察后再考虑 `deny`(评审 M5);永远不得拦截 `agent-kit rsi` 的暂停、回滚、停用命令。任何异常返回 `allow` 并计数——这是可用性策略,所以 **E0 不是安全控制**,只是便利性提示 / 受限阻断;它挡不住 shell 包装、别名、参数编码造成的绕过。超时用可中断的实现(匹配循环内检查步数),不是事后测时。

E1 / E2 为什么不做:macOS 上的现实选项是 `sandbox-exec`(Seatbelt 配置文件,官方已标为弃用但仍可用 [假设 需按系统版本核实])、容器(需要 Docker / colima,本机只做轻活)、`node --permission`(只约束 Node 进程)。它们都只能约束**试跑**;一旦作为钩子被 claude / codex / pi 调用,运行在宿主 agent 的进程树里,沙箱不随行。所以「沙箱试跑通过」不能推出「启用后安全」。用户 U3 的「沙箱试跑通过且观察期无异常才启用」对 E0 成立(解释器固定,数据无执行能力),对 E1 / E2 不成立。若用户仍要 E1,见决定 M5。

### 3.5 预算口径 [推荐]

- 自动产出(`origin=auto_rsi`)占用**单独配额**:每个渲染目标预算的 25%(claude 200 行中 50 行;其他 16384 字节中 4096 字节)。配额是代码常量,配置只能调严。
- 配额内再分:规则 50%、踩坑 30%、技能触发描述 20%。
- 新增改动让配额占用 ≥ 80% 时,同一次改动必须同时退役一条(最久未命中的优先);做不到则不生效。
- 灰度期内候选通过 hint 注入,不占静态渲染预算,但计入「注入字节」成本(§4.4 C4)。

### 4.2 我们的「真值」从哪来

没有基准测试集,也没有人工标注。可用的代理与它们的可靠性:

| 代理                       | 计算方式                                                      | 可靠性                                               | 可被钻空子的方式                                                                        | 用途                        |
| -------------------------- | ------------------------------------------------------------- | ---------------------------------------------------- | --------------------------------------------------------------------------------------- | --------------------------- |
| 目标聚类复发率             | 灰度组 vs 对照组中,候选所针对的那类信号(按签名)每会话发生次数 | 中:直接对应「这条改动想解决的问题」;但签名是代理口径 | 规则让 agent 换个方式犯同样的错(签名匹配不上);规则让 agent 不再调用该工具(失败自然变少) | 主判据                      |
| 工具失败重试链长度         | `retry_chain_len` 均值                                        | 中                                                   | agent 失败后直接放弃不重试(链变短)                                                      | 不得变差                    |
| 显式教训重复出现           | 用户就同一主题再次说「以后 / 不要再」                         | 高(用户亲口),但稀疏                                  | 很难钻,除非规则让 agent 劝用户别说                                                      | 不得变差;出现即强烈变差信号 |
| 会话结局 `session_outcome` | 放弃 / 不对 类比例                                            | 低到中:句式表误判,且受任务难度影响                   | 规则让 agent 更频繁地要求用户确认(增加「确认完成」句式)                                 | 不得变差                    |
| 每会话 token / 注入字节    | 字节数代理                                                    | 中:字节不等于计费                                    | 把内容挪到技能(按需加载)以规避常驻字节                                                  | 不得上升(C4)                |
| 每会话工具调用数           | 计数                                                          | 低:多不一定差                                        | —                                                                                       | 只报告,不判定               |
| 固定测试通过率(§4.3)       | 会话 agent 生成、固定后回放                                   | 低到中:论文没有报告误报率;我们样本更小               | 测试与提案由同一个 agent 写(自评);规则针对测试措辞过拟合                                | 只作 G8 的「不低于现状」    |

由此得出的判定结构:

- **主判据显著变好**(目标聚类复发率下降),且**每项保护指标非劣效**(§4.4:率比的单侧置信上界低于预设界限),才算生效。「没检出变差」不算通过;区间过宽、指标缺失、两组都是零事件,一律判「证据不足」。
- 任一保护指标显著变差就回滚,哪怕主判据变好(防「少做事」式的改善)。
- 「agent 少做事」的系统性风险:加一条「每会话工具调用数」降幅 > 40% 时视为可疑,不生效(只阻止生效,不回滚已生效的)。

### 4.3 固定测试 / 回放在我们场景里怎么做

借用 HarnessPro 的两点:**测试从任务描述与初始执行记录生成、生成后固定、所有候选用同一套**;**两阶段筛选**。

| 步骤         | 谁做                                 | 怎么做                                                                                                                                                                                                                                                                                                           |
| ------------ | ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 生成合成任务 | 会话 agent(S2 续跑,与写提案同一轮)   | 依据聚类的脱敏摘录(只限当前项目,N3)写 1–3 个**合成任务**:prompt + 合成 fixture + **声明式断言**;fixture 只能是合成文件,不复制用户仓库内容                                                                                                                                                                        |
| 断言形状     | kit 固定 schema                      | 只允许:「某文件包含 / 不包含某字面串」「`git diff --stat` 改动文件集合等于 / 属于」「改动行数 ≤ N」「某文件存在 / 不存在」。由 kit 的固定解释器在临时目录里判定。**不接收、不执行生成的 shell**(评审 H11:shell 的替换、重定向、展开让「命令白名单」无法靠静态扫描守住)。现有人工写的 `cases/*/check.sh` 不受影响 |
| 固定         | kit                                  | 测试进私有仓库 `cases/auto/<cluster>/`,哈希写进灰度账;之后该聚类的所有候选、以及「无候选的现状」都用这一套;测试本身过 G1 / G2                                                                                                                                                                                    |
| 执行         | **会话 agent**(用户下一次 S2 续跑时) | kit 不 spawn agent(D5)。agent 在 kit 准备的临时目录(`KIT_TMP` 下)里按 prompt 操作 fixture,然后 kit 判定断言。现状与候选各跑一次(候选的规则文本由 kit 在 prompt 前附上)                                                                                                                                           |
| 筛选(两阶段) | kit                                  | ①淘汰通过率 < 现状的候选;②在剩余候选里淘汰被「通过率更高且注入字节更少」的另一候选同时支配的                                                                                                                                                                                                                     |
| 三种取向     | kit                                  | 见 §4.5                                                                                                                                                                                                                                                                                                          |

诚实评估:

- 这是「同一 agent 出题、同一 agent 答题」:出题时 agent 已经知道要验证什么,测试很可能偏向提案。所以 G8 只用作「不低于现状」的否决条件,**不作为生效的正面证据**。
- 每个候选每个测试只跑一次,噪声大(论文同样一次一跑,未讨论噪声 [论文])。
- 占用户会话额度与时间:一次 S2 续跑里多出 2–6 个小任务。所以固定测试是 Medium / Heavy 档才开,Lite 不开。
- **执行不隔离**:agent 有 shell,临时目录约束不了它访问目录外的文件,也挡不住被 prompt 诱导去操作别处。「合成 fixture 不含值得破坏的东西」只说明临时目录里没有,不说明 agent 碰不到别处。这是固定测试的残余风险,也是它默认只在 Medium / Heavy 开的另一个原因。
- 超时(生成 7 天、执行 14 天)→ 候选进 `blocked`,再 14 天 → `expired`;**不自动降为 Lite**(评审 M2:降档等于用超时绕过用户选定的证据标准)。

## 5. D. 观察期与回滚

### 5.1 个人层候选的生命周期

评审 M9 指出原状态机混用三件事。改为三个正交维度,各自一张转移表(实现时写成 schema + 转移函数,带守卫、幂等键、时钟与恢复行为):

**维度一:候选生命周期**(私有仓库 + `.state/rsi/candidates/`)

| 状态                                   | 进入                                         | 退出                                                                                      |
| -------------------------------------- | -------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `proposed`                             | ingest 成功                                  | G0–G7 全过 → `shadow`;任一红 → `rejected`                                                 |
| `shadow`                               | 闸通过;不渲染、不注入,只统计「若存在会命中」 | 观察满 20 个会话(按会话不按天)且命中 ≥ 2 → `canary`;满 20 会话命中 < 2 → `expired`        |
| `canary`                               | 按会话随机注入 50%                           | 判生效 → `adopted`;判变差 → `rolling_back`;证据不足到上限 → `expired`;G8 超时 → `blocked` |
| `blocked`                              | 等待必需证据(固定测试)                       | 证据到齐 → 回到原状态;14 天 → `expired`                                                   |
| `adopted`                              | 90% 注入、10% 留出                           | 留出组非劣效且累计 ≥ 40 个会话 → `stable`;变差 → `rolling_back`                           |
| `stable`                               | 转为静态渲染(新的部署阶段,§5.4)              | 变差 → `rolling_back`;用户 `veto` → `rolling_back`                                        |

**维度二:本机部署**(每个候选):`none → injected(canary/adopted) → static_pending → static → removal_pending → none`。`static_pending` = 等 safe sync;`removal_pending` = 等撤销路径完成。

### 5.2 影子运行与灰度怎么实现

**为什么不能只做「影子」**:规则是给 agent 读的文本,不加载就不影响行为,所以 shadow 只能测「命中率」(适用面),测不了「效果」。效果必须真正加载,于是要有对照。

**对照对象的三种方案(决定 M4)**:

| 方案                      | 做法                                                                                                                                                                 | 代价                                                                                                                            |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| **A(推荐)按会话随机注入** | 会话开始钩子(claude `SessionStart`、pi `before_agent_start`)调用 `rsi hint`;hint 按 `hash(会话开始时刻, 随机数)` 决定本会话是否附上 canary 文本,把分组写进本机灰度账 | 依赖钩子注入能力(claude 公开文档能做、pi 实测类型能做、codex 未验证 → codex 会话不参与灰度);注入占上下文;每会话都要写一行灰度账 |
| B 前后对比                | 生效前 14 天 vs 生效后 14 天                                                                                                                                         | 混杂:任务类型、项目、季节都会变;小样本下几乎必然误判                                                                            |
| C 按项目分组              | 一半项目加载、一半不加载                                                                                                                                             | 现有渲染是全局的(home 目标),要做项目级渲染,而 project 目标 v1 不处理;项目间差异大,组间不可比                                    |

方案 A 的细节:

- 分组单位是会话;随机源是 kit 的注入随机源,结果写进 `.state/rsi/canary/assign.jsonl`(会话开始时刻、agent、候选 id 集合、组别;无路径)。
- 会话结束后,L0 采集到的信号按「会话开始时刻 + agent」与分组账关联。关联不上的会话不计入(不猜)。
- V1 全局同时只有一个 canary(G7);以后放宽到多个时,每个候选独立随机,且对最终规则集合整体做组合回归(评审 H9)。
- **适用资格在注入前确定**(评审 H8):会话开始时只知道 agent 与项目,资格 = 「该项目在分组前 30 天里出现过目标签名」;不得用注入之后的行为判断「本可命中」(那是处理后筛选)。主分析按分配即分析(ITT):所有被随机的、资格成立的会话都进分母,关联不上 L0 的会话不丢弃,而是计入 C6 并在敏感性分析里按最坏情况填补。
- 注入文本带固定前后标记,`rsi hint` 的 200 字节上限对 canary 不适用,改为单独上限:每会话 canary 注入总量 ≤ 1.5KiB。
- 这要求修订 R20-3.3(hint 只输出计数)与 R20-3.3.4(hint 唯一写入是去重标记),见 §11。

### 5.3 生效判据与样本量 [推荐,数值待 V1.5 校准]

- **门槛由三部分组成**(评审 H7):①每组最少会话数(§4.5);②**最少相关事件数**:对照组目标事件 ≥ 15 次;③**精度要求**:主判据率比的双侧 90% 区间宽度 ≤ 0.6。三者都满足才做生效判定。
- **上限**:每组 120 个会话或 90 天(先到为准),仍未满足门槛 → `expired`。按评审的估算,对照组发生率 0.1 次 / 会话时 20 个会话只有约 2 次事件,门槛②需要约 150 个对照会话,超过上限——**这类低频问题拿不到统计生效,是有意的结果**,它们改走「按需加载的技能」(不常驻、不进静态渲染)。
- **计会话、不计天**:用户不用 agent 时灰度不前进。
- **检验方法**:不假设泊松独立。主判据与保护指标都用**分层置换检验**(按 agent × 项目分层,重随机分组标签 2000 次)得到区间与 p 值;变好方向 α = 0.05 单侧、效应量率比上界 ≤ 0.7(下降 ≥ 30%);保护指标用非劣效界限(§4.4)。
- **固定分析计划**:变差方向每 10 个新会话查看一次,用预先定义的序贯边界(alpha spending,O'Brien–Fleming 型,总 α = 0.10)判定回滚;变好方向只在门槛满足时查看一次、到上限再查看一次(各 α = 0.025)。错误率控制对象是**每个候选**;系统长期的误生效率靠 V1.5 的「无效果模拟」验收(注入无关文本,误生效率必须 ≤ 5%)。
- **V1.5 先做功效模拟**:用本机真实历史信号的发生率与过度离散做重抽样模拟,算出在 120 会话上限内能被检出的最小效应量;若常见聚类都检不出 30% 的改善,则整个「统计生效」通道在本机不可用,循环保持只提示(这是需要如实告诉用户的可能结果)。

### 5.4 变差判据(adopted 与 stable)

- **adopted**:90% 注入、10% 留出(静态渲染后无法让单个会话「不加载」,注入一句「忽略以下规则」也不可靠),留出组上的保护指标按 §5.3 的序贯边界监视。累计 ≥ 40 个有观测会话且非劣效 → `stable`。
- **stable 是新的部署阶段**(评审 M4):注入与静态文件的加载位置、优先级、适用 agent 都不同,灰度证据只对注入模式成立。转静态后:①保留 10% 留出能力需要「按会话不加载静态文件」,做不到,所以改为**影响面限制**——每次只转一个候选、转后 40 个会话内与转前 40 个会话比较保护指标(前后对比,承认其混杂,只用于触发回滚、不用于证明效果);②优先方案是**长期保持注入模式**、不转静态(代价:一直占注入额度,且 codex 会话拿不到),由决定 M12 定。

### 5.5 自动回滚:补偿流程而不是原子事务

停止注入、改私有仓库、重渲染、HOME sync 是不同系统的动作,journal 只能保证可恢复,不能让它们成为原子事务(评审 H10)。所以回滚拆成四个子状态,每个都可独立重试、可续做:

| 子状态                   | 动作                                                                                                       | 完成判据                                 |
| ------------------------ | ---------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| `rollback_requested`     | 写 journal(候选 id、原因、目标集合)                                                                        | journal 落盘                             |
| `injection_disabled`     | 灰度账把候选标为停止注入,hint 下一次调用即不再注入                                                         | 标记落盘(这一步之后**新会话**不再受影响) |
| `static_removal_pending` | 用**候选集合 + 内容寻址快照**重建私有仓库的目标树并提交(不依赖 `git revert` 能干净应用);重渲染本机 payload | 私有仓库 HEAD 的树等于目标树             |
| `rollback_complete`      | 走**撤销路径**同步 HOME                                                                                    | HOME 中该候选的托管块不存在              |

**撤销路径**(独立于 §7.1 的生效路径):只允许「删除自动产出的托管块 / 独占文件」,不受 `auto_paused`、候选状态条件、操作数上限阻挡;仍遵守漂移规则(托管块被用户改过 → 不覆盖,停在 `static_removal_pending` 并提示用户)。为让撤销可以单独进行,**自动产出一律写在独立的托管块或独占文件里**,不与人工内容混在一个块中。

崩溃后由下一次持锁运行按 journal 续做;续做本身再崩溃同样可续。审计日志与 R20-7.1 同形(无路径、无文本),另存 `.state/rsi/audit.jsonl`:按时间保留 365 天、上限 20000 行,超出先压缩为按月汇总再删;灰度分组账保留到候选终态后 90 天,之后只留聚合计数(评审 M10)。会话关联用「会话开始时刻 + agent + hint 生成的随机会话标记」三元组,随机标记写进注入文本的固定前缀,reader 采集时取回;取不回的会话计入 C6。审计只能称「kit 路径可追踪」,同 UID 下不防篡改。

### 5.6 回滚后如何避免立刻重复提出

| 机制         | 内容                                                                               | 与 tainted / 墓碑的关系                                                                                                                                                  |
| ------------ | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 聚类冷却     | 自动回滚:该聚类冷却 90 天;`expired`:30 天;冷却期内不进 digest                      | 独立于 tainted:tainted 是隐私处置,冷却是质量处置                                                                                                                         |
| 文本指纹     | 规范化正文的 HMAC(本机密钥,不用裸哈希,防字典猜测)与近似指纹,与冷却同期失效         | 只存指纹;近似指纹本身会泄露文本的部分特征,所以只在本机、不进团队 PR(评审 L2)                                                                                             |
| 用户否决     | `rsi veto` 的候选:指纹永久黑名单;解除只能前台 `rsi veto --lift <id>`(TTY),并写审计 | 与自动回滚冷却分开,避免永久误伤后来的正确修复                                                                                                                            |
| id 墓碑      | 终态候选的 id 进墓碑,C7 拒绝复用                                                   | 与现有墓碑同一机制                                                                                                                                                       |
| tainted      | 证据项目被排除 / purge:候选永远不能进灰度或生效;已生效的进 `rollback_requested`    | **N6 扩展**。「立即生效」的承诺收窄为(评审 M8):写下排除后,下一次 hint 调用起**不再注入**、不再用作新证据;静态撤销与远端撤销各自报告完成状态;已进入模型上下文的内容收不回 |
| 私有仓库历史 | 回滚提交不会删掉历史里的文本                                                       | `rsi purge` 对私有仓库额外做历史改写(重建不含该候选的历史)并在 `rsi status` 报告;备份与 Time Machine 不在 kit 管辖范围,照写                                              |

## 6. E. 自动合并流水线(团队层)

### 6.1 团队晋升条件 [推荐]

候选在个人层 `stable` 且静态阶段累计 ≥ 40 个有观测会话无回滚,并且:

- 证据来自 ≥ 2 个项目,这些项目的 key 都在 `team_project_keys` 白名单(现有 C4 层规则);
- 类别是规则或踩坑或技能(不含数据化可执行物、子代理);
- 不在 `auto_paused`。

**这些条件全部是本机判断,服务端无法验证**(评审 H5)。团队 PR 带的 `lifecycle/auto/<id>.json` 只能证明「报告格式对」,不能证明「真的稳定过」。

### 6.2 身份与凭据(评审 H1 后改写)

能向原仓库推任意非保护分支的凭据,等于能在原仓库的 `push` 事件下执行任意工作流代码,进而尝试读取仓库级 secret、使用 `GITHUB_TOKEN`。所以投稿凭据不能落在原仓库上。

| 方案                                                                                                                                                                                                            | 投稿凭据能做什么                                  | 合并凭据在哪                                                                  | 代价                                                                                                                                    |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- | ----------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| **A(推荐)独立投稿仓库**:用户新建一个私有仓库 `agent-kit-rsi-inbox`,本机用只对它有写权限的部署密钥推候选;原仓库的定时工作流(默认分支)只读取投稿仓库的**数据文件**(规则正文与报告),在原仓库里由 App 生成分支与 PR | 只能改投稿仓库;碰不到原仓库的工作流、secret、分支 | 原仓库 environment `rsi-automerge`,部署分支策略只允许 `main`;App 私钥只在其中 | 用户多建一个仓库与一把读取它的凭据(放在 environment 里);原仓库工作流要把投稿内容当不可信数据处理                                        |
| B 原仓库部署密钥 + environment 限定的 App 私钥                                                                                                                                                                  | 能推原仓库任意非保护分支、触发 `push` 工作流      | 同上                                                                          | 要逐项证明:所有 `push` / PR 工作流拿不到 environment secret、默认 `GITHUB_TOKEN` 只读、无仓库级 secret;任何一个新工作流都可能破坏这一点 |
| C 用户本人 `gh` 登录                                                                                                                                                                                            | 一切                                              | —                                                                             | 用户是 admin,可能有发布能力(G4);**不可接受**                                                                                            |

两种方案共同的服务端要求:原仓库**默认 `GITHUB_TOKEN` 权限设为只读**;不设仓库级 secret(现有 secret 盘点后迁入 environment);`npm-publish` 与 `rsi-automerge` 两个 environment 的部署分支都只允许 `main`(及发布用的 `v*`)。这些都是 V4 开工前的实测项(§10.2 V4a)。

### 6.3 流水线(方案 A)

```
本机 publish worker                 原仓库(默认分支上的工作流,App 身份,environment=rsi-automerge)
──────────────────                  ──────────────────────────────────────────────────────────────
team eligible
 └─ 在投稿仓库写 candidates/<id>/
    {rule.md, report.json}(无摘录)
 └─ git push(投稿仓库)  ───────────► rsi-intake(schedule,每小时)
                                         ├─ 读投稿仓库数据(不执行其中任何内容)
                                         ├─ 查服务端否决记录与 RSI_AUTOMERGE 开关
                                         ├─ 在原仓库按 base 生成补丁 → 分支 rsi/team/<id> → 开 PR,标签 kit:auto-rsi
                                    ───► ci.yml 的 verify / supply-chain(必需检查)
                                    ───► rsi-scope(必需检查;pull_request_target,只检出 base,
                                         用完整 tree / blob 比较读 PR 内容,不执行 PR 代码)
                                    ───► rsi-automerge(schedule)
                                         合并授权元组:PR 号 + head 提交 + base 提交 + 策略版本 + 可信检查结果
                                         条件:元组内检查全绿(检查来源限定为 GitHub Actions 集成)
                                               + 该 head 首次全绿时刻起 ≥ 72h(时刻由 rsi-scope 写在检查结果里)
                                               + 无 kit:veto 标签、无 request changes、候选 id 不在否决记录
                                               + RSI_AUTOMERGE 不为 off
                                         └─ 调合并接口并带预期 head 提交号(head 变了即失败);squash
本机下一次 publish worker
 └─ git fetch 原仓库,识别 merged / closed / vetoed
```

`rsi-scope` 的判据(服务端执行,不信本机;评审 M6 后补全):

- 用完整 tree / blob 比较(不用分页的文件清单,任何内容读不全 → 拒);
- 改动只在 `rules/team/**`、`skills/auto-*/**`、`lifecycle/auto/**`;只允许 `.md` 与 `.json`;文件模式只允许 100644;禁止符号链接、子模块、重命名、删除、二进制;
- 「是否为自动产出」看 **base 里的原始归属**:修改已有文件时,base 版本必须已带 `origin: auto_rsi`;人工文件不能被改成 `auto_rsi` 后被自动修改;
- 不触碰 `.github/**`、`src/**`、`test/**`、`ops/**`、`scripts/**`、`package.json`、`pnpm-lock.yaml`、`CODEOWNERS`、`kit.toml`、`rules/org/**`、`cases/**`;`skills/auto-*/` 下只允许 `SKILL.md`;
- 证据 `excerpt` 全为空串,`ref` 只能是随机 id(不用原文哈希,防字典猜测,评审 M7);
- 全文过 base 版本 kit 的脱敏器 pass2 与话术扫描;
- 单 PR ≤ 3 个原子、≤ 8KiB;`lifecycle/auto/<id>.json` 过 schema(只有计数、比率、日期);
- 检查结果里记录本次评估的 head 提交号与首次全绿时刻;head 变化 → 时刻重置。

为什么用 schedule / `pull_request_target`:`push` / `pull_request` 事件运行的是被推分支里的工作流文件(G6)。`pull_request_target` 以 base 权限运行,若检出并执行 PR 代码会泄露 secret,所以 `rsi-scope` 不检出 PR 代码、不执行 PR 内容;它产生的检查与 PR head 提交的关联方式要在 V4a 实测(评审 H2)。

**否决与暂停在服务端**(评审 H4):

- 全局:仓库变量 `RSI_AUTOMERGE=off`,用户在 GitHub 界面改,所有自动合并立即停止;
- 单个:PR 加 `kit:veto` 标签或关闭 PR → `rsi-automerge` 把候选 id 与内容指纹写进原仓库 `lifecycle/auto/vetoed.json`(经同一流水线的 PR 合入,或存在 environment 外不可被投稿方写的位置 [假设 选型待 V4a]);之后同 id 或同指纹的投稿一律拒,重建分支不能复活;
- 本机 `rsi veto <id>`:本机立即撤销个人层;对远端只能「请求」——publish worker 在投稿仓库写撤回记录,`rsi-intake` 读到后给 PR 加 `kit:veto`;在看到远端确认前,`rsi status` 显示「远端仍可能合并」。

### 6.4 与 CODEOWNERS、必需检查的关系

- 现状(G2 / G3):main 没有审查规则,CODEOWNERS 不构成合并门。自动合并因此**不需要绕过任何东西**。
- U4「保留 CODEOWNERS 与必须通过的检查」的落实:①必需检查从 2 个增加到 3 个(`verify`、`supply-chain`、`rsi-scope`),并把检查来源绑定到 GitHub Actions 集成(规则集现已绑定 integration_id,新增项照此);②CODEOWNERS 保留并给 `rules/team/`、`skills/auto-*/` 加显式条目;③72h 否决窗口。
- **必须如实告诉用户**:保留 CODEOWNERS 文件只是通知,不是审批保障;U4 里「保留 CODEOWNERS」在现状下不提供任何拦截能力。若要它成为合并门,就得加「要求 code owner 审查」,自动合并随即做不到(App 不是 code owner)。决定 M7。

### 6.5 发版是否纳入自动 [推荐不纳入]

- 合入 main 不等于用户本机生效:本机生效走本机 payload(§7),不依赖 npm。
- npm 发版会把改动发给所有装了包的人;公开仓库 + 无人审批的规则一旦发版,影响面从「我自己」扩到「所有用户」,且 npm 版本不可撤回(只能弃用)。
- 发版需要建 v\* tag,自动流程按 §6.2 设计本来就建不了;保持这个能力缺失本身就是护栏。
- 所以:发版保持人工(打 tag)。`rsi status` 显示「main 上自上次发版以来的自动合并数」,提醒用户。

## 7. F. 本机生效

### 7.1 与 §19.6 的衔接

本机生效 = 「本机 payload」经 `safe` 条件写入 HOME。条件表逐条处理:

| §19.6 条件                                  | v3 处理                                                                                                                                           |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto_sync = "safe"` 且 `KIT_AUTO_SYNC ≠ 0` | 保留;另加 `[rsi.auto] enabled = true`                                                                                                             |
| 登记表已存在(永不首装)                      | 保留                                                                                                                                              |
| 无残留 txn                                  | 保留                                                                                                                                              |
| 同一 major                                  | 保留(本机 payload 的 `kit_version` 取当前 kit)                                                                                                    |
| 无漂移 / 无外来冲突 / 无共用路径冲突        | 保留                                                                                                                                              |
| 全部是 instructions 类                      | 保留;数据化可执行物不走 sync,走 §7.4 独立通道                                                                                                     |
| 新建 / 更新的原子无 `must`                  | 保留(G4 已保证自动产出只有 `should`)                                                                                                              |
| 重扫干净                                    | 保留                                                                                                                                              |
| `integrity.json` 核对 + 外部锚点            | **改**:本机 payload 由 kit 本机渲染,锚点 = 渲染时记下的 `integrity.json` sha256,存在 `.local/state/agent-kit/rsi/local-payload.json`;核对语义不变 |

| (新)只含 `origin=auto_rsi` 文件的变化       | 新增:本机 payload 相对上一次已同步版本的差异,只允许出现在自动产出文件上;其他差异(例如用户改了仓库但没发版)→ `declined local_non_auto_diff`        |
| (新)候选状态为 stable                       | 新增:差异里的每个自动产出文件必须对应一个处于 stable 的候选(adopted 阶段只经 hint 注入,不进静态渲染)                                              |

本机 payload 的组成:npm 包内 payload(当前 `current` 版本)+ 私有仓库里 stable 的个人层产出(personal 层在本机渲染,修订 §4.2)。团队层合入 main 的内容在**下一次 npm 发版**后才通过包 payload 进来;在那之前,同一条内容仍由私有仓库提供(状态 `merged`,去重以免重复渲染)。

### 7.2 两种 payload 的隔离

- 包 payload 与本机 payload 分别登记来源;登记表条目增加 `source: package | local`(契约修订)。
- 本机 payload 永不进 npm 包;构建发布包的 `check-publish` 增加断言:payload 中不存在 `layer=personal` 或 `origin=auto_rsi` 且未在仓库 `rules/team/` 中的条目。
- `sync --rollback` 对两种来源一视同仁(都是事务)。

### 7.3 可执行类(E0 数据化)的本机启用路径

1. 用户一次性安装解释器入口(pi:`rsi hooks --install --agent pi` 写扩展,TTY 确认,v2 A5 已规划;claude / codex:打印片段由用户贴,N1)。安装后的入口调用 `agent-kit rsi exec-check`。
2. 自动循环把通过闸与灰度的 `ExecData` 条目写进私有仓库 `exec-data/`;kit 把**启用集合**物化为 `~/.local/state/agent-kit/rsi/exec-data.json`(kit 状态目录,在写入表内,不需要改 settings)。
3. 灰度:`exec-check` 按会话分组决定是否应用该条(与 §5.2 同一份分组账)。
4. 总开关:`[rsi.auto] exec_data = false`(缺省)时 `exec-check` 恒 `allow`;`KIT_AUTO_RSI=0` 同样恒 `allow`。
5. 审计:每次 `deny` / `warn` 写一行(条目 id、动作、时间;不写命令参数)。

## 8. G. 循环的驱动

### 8.1 阶段状态机与触发者

| 阶段                  | 触发者                                 | 做什么                                                           | 可能卡住的点                     | 超时 / 重试 / 熔断                                                                   |
| --------------------- | -------------------------------------- | ---------------------------------------------------------------- | -------------------------------- | ------------------------------------------------------------------------------------ |
| ① 采集 L0             | 会话结束钩子 → poke → worker(已有,§20) | collect + 分类 + 聚类计数                                        | 钩子不触发;熔断                  | 沿用 R20-6                                                                           |
| ② 提案                | 会话 agent(S2 续跑;S1 用户要求)        | digest → 写提案 → ingest                                         | 用户不开 S2;agent 写不出合规提案 | 每天每 agent ≤1 次;连续 5 次 ingest 被拒 → 该聚类冷却 7 天                           |
| ③ 闸 G0–G7            | worker(ingest 之后的下一次持锁运行)    | 确定性检查                                                       | 闸内部错误                       | 内部错误 → 熔断 B2                                                                   |
| ④ 生成固定测试(M / H) | 会话 agent(与②同轮或下一轮 S2)         | 写 1–3 个合成 case(声明式断言)                                   | 没有 S2 机会                     | 7 天内没生成 → `blocked`;再 14 天 → `expired`(不降档)                                |
| ⑤ 执行固定测试        | 会话 agent(S2)+ kit 判定               | 现状与候选各跑一次                                               | 同上;agent 跑偏                  | 每次 S2 最多 6 个 case;14 天内没跑完 → `blocked`                                     |
| ⑥ shadow              | worker(每次 L0 后)                     | 签名命中统计                                                     | 无新信号                         | 满 20 会话命中 < 2 → `expired`                                                       |
| ⑦ canary              | hint 钩子(分组注入)+ worker(评估)      | 分组、注入、每 10 会话评估                                       | codex 会话不参与;用户不用 agent  | 每组 120 会话 / 90 天 → `expired`;变差即回滚                                         |
| ⑧ adopt / stable      | worker                                 | adopt:私有仓库提交、90% 注入;stable:本机 payload 渲染、safe sync | safe 条件不满足                  | 不满足 → `SYNC_PENDING` 提示,候选停在 `adopt_pending` 并继续注入;7 天 → 回滚         |
| ⑨ stable 监视         | worker                                 | 留出组与控制图                                                   | —                                | 变差 → 回滚                                                                          |
| ⑩ 投稿                | publish worker(`__rsi --publish`)      | 写投稿仓库、`git push`                                           | 网络;部署密钥失效                | 每天 ≤1 次推送;失败 3 次 → 停团队通道并提示                                          |
| ⑪ PR / 合并           | 原仓库工作流(App)                      | 开 PR、scope 检查、当前 head 全绿起 72h 后合并                   | 检查红;用户否决;head 变化        | 检查红 → 关闭 PR,团队维度终止并冷却 30 天;否决 → 同上 + 服务端否决记录 + 熔断计数 B9 |
| ⑫ 收尾                | publish worker(fetch)                  | 识别已合并 / 已关闭                                              | —                                | —                                                                                    |

publish worker 的触发:poke 与 L0 共用节流,但 publish 是单独入口,只在 L0 完成且存在待推候选时由 worker 再起一个 `__rsi --publish` 进程(它的 import 闭包允许 git 网络操作,不允许 `net.ts`)。因此 L0 worker 的 **import 闭包**仍零联网,但它的**子进程能力**不再是零联网(评审补列);契约要区分这两者。

### 8.2 用户不用 agent 时

- ①②④⑤ 停止;⑥⑦ 不前进(按会话计数);⑧⑨ 不变化;⑩⑪⑫ 可继续(只需 kit 某个命令触发 poke 或用户手动 `rsi tick --write`)。
- 恢复:下一次会话结束 → poke → worker 从当前阶段接着走;灰度账按会话追加,无需重置。
- 不会发生「长期不用 → 到期自动生效」。可能发生「长期不用 → 到期 `expired`」(45 天上限),这是有意的保守方向。

## 9. H. 度量与可见性

### 9.1 `rsi status` 新增字段(`--json` 固定键)

`auto`:`{enabled, paused, pause_reasons[], profile: lite|medium|heavy}`;`pipeline`:各阶段候选数 `{proposed, rejected_30d, shadow, canary, adopt_pending, adopted, stable, team_candidate, team_pr_open, merged_30d, rolled_back_30d, expired_30d}`;`budget`:`{auto_quota_used_pct_by_target}`;`cost`:`{inject_bytes_per_session_7d, baseline}`;`canary`:`[{id, kind, sessions_treat, sessions_ctrl, status}]`(只有 id 与计数);`team`:`{open_prs, merges_since_last_release}`;`last_rollback`:`{at, id, reason}`。

### 9.2 周报

- 每周第一次会话开始时,hint 输出一行(计入 200 字节):`agent-kit RSI 周报:生效 a、回滚 r、灰度中 c、待合并 PR p、预算 q%。详情 agent-kit rsi report`。
- `agent-kit rsi report [--week|--since <日期>]`:列出期间每个生效 / 回滚的 id、类别、指标前后值、私有仓库提交 id;不含正文(正文用 `rsi show <id>`,TTY 下显示、剥控制序列、标「自动产出」)。
- 团队 PR 打开时,仓库侧工作流在 PR 里列灰度报告;用户已有的飞书通知流程可订阅 PR 事件(不在本稿实现)。

### 9.3 一键操作

| 命令                                       | 作用                                                                                               |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| `rsi auto pause` / `rsi auto resume`       | 进入 / 退出 `auto_paused`(resume 需 TTY)                                                           |
| `rsi veto <id>`                            | 本机立即进入 `rollback_requested` 并永久黑名单;远端只能请求(§6.3),确认前显示「远端仍可能合并」     |
| `rsi rollback --to <YYYY-MM-DD> [--write]` | 回滚该日期之后生效的全部自动产出(按生效顺序逆序逐个回滚事务;默认干跑列清单)                        |
| `rsi auto clear [--write]`                 | 撤掉全部自动产出:停止所有注入、私有仓库回到「无自动产出」提交、本机 sync 移除;不删审计日志与黑名单 |
| `rsi stop`(已有)                           | 连采集一起停                                                                                       |
